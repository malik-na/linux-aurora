# omacom/linux-aurora#177 against aurora-silicon/linux#363 (J516C)

Date: 2026-10-22. Read-only comparison, nothing booted.

- **Ours:** aurora-silicon/linux#363, head `t6031/silicon-g15c` = `e272b673d711`, base
  `j514s/m3-pro-20261017`. It has 35 commits: 33 by Naeem, 2 by Chris (the T6031 GPU and display DT nodes).
- **Theirs:** omacom/linux-aurora#177 (draft), head `review/siliconforest-kernel-20261022` =
  `6d31ee55c5bf`, target `integration/aurora` = `70d5dced`.
- **Method:** each of our commits was paired with a #177 commit by subject, or else by
  content. The +/- lines of each pair were diffed. The final trees were then compared in
  `drivers/gpu/drm/asahi/g15`, `drivers/gpu/drm/apple`, `drivers/soc/apple`, the T6031 DT
  and `include/uapi/drm/asahi_drm.h`. Both trees keep G15 in `drivers/gpu/drm/asahi/g15/`.

## Other #177 G15 changes that touch J516C paths

- **Device-wide logical queue capacity** (1bfbde601610): the 59th live queue gets ENOMEM.
  The QUEUE_LIMITS answer (58/2) is unchanged. Low risk for a desktop. A wide parallel
  dEQP run with many live contexts could hit it.
- **Errored-dependency refusal** (4aa5a5a9b1c6, 186b2143a9ab): every start checks the input
  fences. A foreign device-loss error becomes ECANCELED for a healthy VM, and is reported
  before that job's fence signals. This only changes behaviour after a fault.
- **ABI isolation** (80374c2d267c, b90f94097c30, `g15/wire.rs`): G15 decodes a private native
  layout, and the canonical header changed. See the next section.
- **Firmware start deferred until module registration completes** (cbb678e9a11b,
  `MODULE_READY` + `asahi_g15_reprobe()`), and driver data is allocated before firmware is
  touched (3d5eff3c69fa). These only change probe order.
- **Display-registration gate before GPU admission** (9e92539b4595, 75975401f385): applies to
  `apple,agx-t6030` only. T6031 is explicitly unchanged. It adds the Kconfig dependency
  `DRM_APPLE=y || (DRM_APPLE=m && DRM_ASAHI=m)`.
- **Stats record loads ordered before use** (76d0a346ddd5): a fix, safe for J516C.
- **T6031 DT reserved-memory renamed with unit addresses** (514a11e36758): m1n1 finds the
  nodes with `fdt_path_offset("/reserved-memory/uat-ttbs")`. libfdt matches a component
  without a unit address against `name@addr`, and the kernel reads the regions through the
  GPU node's `memory-region` phandles. #177 states that its new DTBs are not
  hardware-qualified.

## Mesa / UAPI compatibility (aurora-silicon/mesa#25, aab698d2)

- The canonical `include/uapi/drm/asahi_drm.h` in #177 is **not** what our Mesa was built
  against:
  - Feature bits are renumbered: PER_COMMAND_INPUT_SYNCS 3->10, VM_STATUS_MIRROR 4->11,
    EXACT_PRIOR_BARRIERS 5->12, FEW_PRIMITIVES 6->13, FRAGMENT_BARRIERS 7->14,
    RENDER_RAY_QUERY 8->15. Bits 3-8 are reassigned (SCHEDULED_QUEUES, timestamp copies,
    FRAGMENT_DEPENDENCY, ...).
  - `ts_frag_end_copies[8]` / `ts_end_copies[8]` are added, giving render 448 B
    (`prior_vdm` at 320) and compute 200 B (`scs_layout` at 128).
  - `vm_create.pad` becomes `flags`.
- The G15 backend does not use that header. `g15/wire.rs` keeps the native layout:
  - Render is 384 B, with `prior_vdm` at 256, `prior_cdm` at 264 and `ray_query` at 272.
    256- and 272-byte packets are zero-filled.
  - Compute is 136 B, with `scs_layout` at 64, `prior_vdm` at 72 and `prior_cdm` at 80.
  - The feature word uses native bits 0-8: 0x3e, or 0xbe with `g15_early_tiling`.
- Mesa aab698d2's `include/drm-uapi/asahi_drm.h` was compiled on the host to check the
  layouts:
  - `drm_asahi_cmd_render` is 256 B, `_with_prior` 272 B (prior_vdm 256, prior_cdm 264) and
    `_with_ray_query` 384 B (ray_query 272).
  - `drm_asahi_cmd_compute` is 64 B and `_with_prior` 136 B (scs 64, prior_vdm 72,
    prior_cdm 80).
  - Feature bits are 3..8 as above, and `vm_create` sends `pad` = 0, which reads as
    `flags` = 0 (legacy).
- **Verdict:** compatible. The wire offsets, sizes and feature numbers that Mesa aab698d2
  uses are exactly the ones #177's G15 backend decodes and advertises, and our #363 kernel
  advertises the same 0x3e word. A Mesa rebuilt against #177's *canonical* header would not
  match G15. Mesa must keep its own header.

## Enabling native G15 on a J516C with #177

- **Kconfig:**
  - `CONFIG_DRM_ASAHI_G15=y` (default n), with `DRM_APPLE=y`, or `DRM_APPLE=m` and
    `DRM_ASAHI=m`.
  - It selects `APPLE_T6030_GPU_PMP_LINK`, which depends on `APPLE_T6030_DISPLAY_GATE`
    (default ARCH_APPLE; needs OF_DYNAMIC and OF_OVERLAY). That gate also carries the T6031
    display handoff.
  - `RUST_FW_LOADER_ABSTRACTIONS` must come from APPLE_AOP or APPLE_SEP, because G15 no
    longer selects it.
  - `CONFIG_EXTRA_FIRMWARE="asahi/t6031-j516c-board.bin"`, as before.
- **Driver binding:** with G15=y, the maintained driver's table drops `apple,agx-t6031`, and
  the G15 adapter binds it. T6031 has **no module alias**: only T6030 has
  `MODULE_OF_TABLE_G15`. With `DRM_ASAHI=m`, asahi has to be loaded explicitly (modprobe or
  modules-load.d), the same as on #363. Built in, it probes once the module activates.
- **Module parameters:**
  - None is needed to boot. The defaults are `g15_pb_max_blocks` 3072,
    `g15_idle_standby_us` 0 (the DT value), `g15_recovery` 1 and `g15_stream_gate` 1.
  - `g15_pb_blocks`, `g15_pb_reclaim`, `g15_pb_idle_ms` and `g15_pb_reclaim_blocks` do not
    exist on #177. A command line that sets them only gets an unknown-parameter warning.
- **DT:** the T6031 GPU node, its `agx_mbox`, and the display nodes are `status =
  "disabled"`. The loader sets the GPU to okay, fills the UAT regions and the firmware
  words, and marks the display with `apple,t6031-handoff = <1>`. These are the same rules
  as #363.
- **Display:** off unless requested. `apple_t6031_display.enable=1` makes the gate enable
  the DCP, mailbox, DARTs and display subsystem. It also completes the DT PMP topology with
  the values in `/chosen/asahi,t6031-pmp`, and requires PMP image 07FF4C5B. Without the
  switch the GPU still starts, because the display-registration gate is T6030 only, but the
  boot framebuffer stays.

## Risks for the J516C on #177

1. **PB exhaustion / fail-stop (high).** There is no idle reclaim and no client-boundary
   re-init. On the J516C a second run of one dEQP list exhausted the 512 MiB heap and
   fail-stopped. Four back-to-back heavy scenes (about 1420 blocks each) hung the GPU into
   fail-stop. Both were measured on the 512 MiB-heap state, which is #177's logical state.
2. **Growth latency (medium).** Chunks are allocated synchronously while the firmware waits
   on a growth request (`__GFP_RETRY_MAYFAIL`, no bound). Ours kept one 16 MiB chunk in
   reserve and allocated after the reply. Under memory pressure a request may miss the
   deadline.
3. **Boot RAM (low).** 128 MiB is pinned at GPU start and grows to at most about 512 MiB,
   never returned before reboot. Ours started at 32 MiB.
4. **Presentation (medium, display only).** Without the 14.7 swap-timestamp fix the
   120 Hz panel presents at 60 fps.
5. **Panel EDID (low).** eDP-1 has an empty `edid` property.
6. **PMP display path (unqualified).** The DT-reuse gate plus the PMP report start replaces
   our T6031 PMP display table. It has not been run on an M3 Max.
7. **Renamed reserved-memory nodes (low).** The new DTB has not been booted on a J516C.
8. **Queue cap (low).** 58 live logical queues per device.
