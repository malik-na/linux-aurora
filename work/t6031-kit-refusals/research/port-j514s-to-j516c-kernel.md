# Porting map: aurora-silicon/linux #358 (J514S, T6030/G15S, Rust `drm/asahi/g15/`) to J516C (T6031/G15C)

Date: 2026-10-18. Read-only analysis; nothing booted, pushed or commented.
Sources: `silicon/j514s` = `j514s/m3-pro-20261017` (PR head `79d6375f4b03`), `silicon/aurora-wip` (tip `070c8e4d43a4`), PR base `0daed2db4787`. Our fork: `t6031/overlay` (`3eb3e456a891`). File:line refs for our fork are on `t6031/overlay`; refs for #358 are `silicon/j514s:drivers/gpu/drm/asahi/g15/<file>` unless stated.
Labels: **OBSERVED** = read in code/logs/results cited; **INFERRED** = my reading, not tested.
Clean-room note (ADR 0001): everything below is facts and structure. Any port is written fresh in our own words; #358 is the other team tree, so no pasting of its expression even though it is in the Aurora family.

## 0. Headline findings

1. **#358 and our fork are two independent M3 implementations, not two ports of one.** OBSERVED: `silicon/aurora-wip` has no `m3_*.rs`, no `hw/t6030.rs`/`t6031.rs`, no `g16_*`; our fork has no `g15/`, no `Uat::new_adopted`, no `mmu/lifetime.rs`. The shared-layer hooks #358 adds are small (about 600 lines: `asahi_core.rs` +62, `driver.rs` +44 `probe_g15`, `file.rs`, `gem.rs` +44, `gpu.rs` +27, `mmu.rs` +203, `mmu/lifetime.rs` +9, `pgtable.rs` +173, `regs.rs` +15 `sgx_read32_at`/`sgx_write32_at`, Kconfig, `rust/kernel/platform.rs` `suppress_bind_attrs`), but those shared files differ from ours by 1000+ lines each (`mmu.rs` +1392/-1203, `gpu.rs` +1927/-185 against aurora-wip), so the hooks do not apply cleanly to `t6031/overlay`.
2. **Every chip-specific T6030 value in #358 is already identical to our own T6030 table.** OBSERVED: its firmware TEXT SHA-256 (`11e49f75...93d5`), TEXT 0x5c000 / DATA 0x114000 / GKTS marker 0x58e88, hw id 0x07031100/0x00110209, the 15-slot IOMAP table with VAs, canonical VAs (ROOT 0xfffffc204062ff40, HWDATA 0xfffffc20406fb5fc, ...), root magic 0x0c08e21e83800490, layout sizes (hardware 35332, globals 15868, power 2292, runtime 0x4b3, control 0xc3d0) all match `m3_firmware.rs:30-49,124-131`, `m3_soc.rs:270-311`, `m3_init_storage.rs:45-72,189-204`, `m3_init_layout.rs`. So the T6031 deltas we have already measured are exactly the deltas needed in #358's tables. #358's novelty is the engine (classic-ring submission, slots, prefixes, recovery, UAT adoption), not the chip facts.
3. **#358 is fixed-image: board data is a hash-checked T6030 template**, with only DVFS rebuilt from the ADT (`board.rs from_adt`, `board/data.rs` 35332 B hardware, 15868 B globals, 2292 B power, each verified by SHA-256 at boot). A J516C cannot use it: our J516C hardware record is 0xb480 bytes (t6031_knobs.rs:769), 376 hardware + 7 globals + 2 power words differ from the T6030-shaped image (overlay, m3_adt_config.rs:1077-1120), and J516C has per-cluster voltage tables. The template mechanism must be replaced by a "build from ADT + J516C words" path, or by a second hash-pinned J516C template.
4. **Two #358 assumptions that fail on J516C by construction:** `collect_perf` demands `perf-state-table-count == 1` and 14 states (adt.rs); J516C ADT has 4 voltage tables (`perf-state-table-count 4`, t6031_knobs.rs / hw/t6031.rs:27-30). `parse` demands `compatible == "gpu,t6030"` for `/arm-io/sgx` and the `gfx-asc/iop-gfx-nub` node name; the J516C node names/compat are INFERRED to be `gpu,t6031` (not verified here).

## 3. What else J516C needs that #358 lacks

**dts.** OBSERVED:
- `silicon/aurora-wip` and `silicon/j514s` have `t6031.dtsi`, `t6031-j516c.dts`, `-base`, `-die0`, `-dieX`, `-pmgr`, `-nvme`, `-gpio-pins`, but **no `t6031-gpu.dtsi` and no `t6031-dcp.dtsi`** (and no `t6030-gpu.dtsi`/`t6030-dcp.dtsi`; for T6030 #358 synthesizes the GPU/PMP/mailbox nodes in C at boot instead). Our fork has `t6031-gpu.dtsi` (commit `fbb86988b8b9`, "describe the GPU, disabled"), `t6031-dcp.dtsi`, `t6030-gpu.dtsi`, `t6030-dcp.dtsi`.
- Our `t6031-gpu.dtsi` is a disabled shell: boot loader fills OPPs (4 voltage cells), CS/AFR OPPs, the four UAT reserved-memory regions, `fw-text`/`fw-data`, `apple,firmware-*`, then enables it. #358 instead reads all of that from the ADT phram export, so one of the two data paths has to be chosen. Our m1n1 already exports `phram` "adt" (`~/Projects/m1n1/src/kboot.c:3070-3095`, OBSERVED in source; whether the aurora17 build we boot has it enabled is not checked).
- The `compatible` string in `OF_TABLE` and in `pmp-display.c` (`apple,agx-t6030`) must also accept `apple,agx-t6031`, or the T6031 DT's `apple,agx-t6031` node never binds.
- PMP: `j514s-pmp-handoff.c` is a T6030-only bootstrapper (hard-coded PA/IRQ, `apple_pmp_t6030_board()` = j514s/j516s compat). T6031 PMP is the kit/our `t6031/pmp-image` path. INFERRED: #358's `apple_pmp_j514s_gpu_*` supplier is not usable unchanged.

**Multi-die.** OBSERVED: T6031 is one die for the GPU (`num_dies = 1`, `hw/t6031.rs:33`, J516C ADT); `-die0`/`-dieX` dtsi exist for other blocks only. #358 hard-codes `num_dies = 1`. No second-die GPU handling is needed for J516C. T6032 (Ultra-class, `t6032*.dts`) is a different later problem. J516C has CS and AFR clock domains (cs-perf-states, afr-perf-states) that #358 does not model (`has_csafr: true`, `hw/t6031.rs:76`); whether the firmware needs them is INFERRED yes (our records publish them; `csafr` knob).

**Display (DCP).** #358's DCP work is 14.7-interface, J514S panel, DCPEXT0/1, HDMI audio, PMP display hold, DART 5-cell etc. (roughly 40% of the PR by lines, the rest is the g15 GPU module). None of it applies to J516C. Our display lives on `t6031/dcp-image` (native display runs) and `t6031/panel-edid`. OBSERVED. For the GPU goal only the "display is up before `modprobe asahi`" ordering matters (OBSERVED in #358's `Driver` doc comment: no module alias).

**Firmware build pins.** Our J516C runs RTKit-2419.140.12 (OBSERVED, `m3_firmware.rs:130`). #358 pins one TEXT hash of the 14.7 stub iBoot-10151.140.19.700.2. See Risk 3: our own earlier boot logs (2026-10-12) read "OS FW version: 14.7 (iBoot-10151.140.19.700.2), System FW mBoot-20457.1.29"; the brief gives OS FW iBoot-10151.140.19.702.3. The hash must be taken from the stub that is installed now.

**Other.** Kconfig/defconfig fragment for J516C (`j516c.config`, analogue of `j514s.config`): `CONFIG_OF_DYNAMIC` only if the handoff is kept. Firmware blob `t6031-hwdata-overlay.bin` via `CONFIG_EXTRA_FIRMWARE` if the overlay words are kept (off-tree). Thermal: our fork has `m3_thermal*.rs` (no pstate above cap 1 without it); #358 has none and runs all ADT states.

## 4. Proposed sequence (one change per boot)

Prerequisite decision (Naeem/team): **base**. Recommended (INFERRED, lowest risk): start a new branch **off `silicon/j514s`** (their engine, UAT adoption and shared-layer hooks already consistent) and add T6031 as a second `Config` row there, supplying facts from our fork; do not try to rebase their hooks into `t6031/overlay`. Ours stays the reference/bisect tree for facts. Mesa: agx3b (`~/Projects/mesa-aurora`, already maps variant 'C' to G15C; needs the USC-window base-page fix).

Boots (each with full dmesg, nothing else changed; parameters as in the brief where they apply; keep `asahi.m3_expose`-style opt-in):
1. **B0, control**: current `t6031/overlay` kernel with the brief's parameters; confirm the baseline compute check passes again with the Mesa USC-window fix (so later regressions are attributable to the port). Proves the J516C/Mesa side is known good.
2. **C1, identity only**: #358 branch + `Config` row `t6031::CONFIG` (chip 0x6031, S->C, rev 0x12, 4x10, hw id masks), compatible match, 40-bit core-mask read, *admission only* (no firmware-visible write; #358's own "admission then start" split makes this a clean stop). Prints the TEXT identity (full SHA-256, GKTS offset, sizes) and the ADT regions. Proves: binding, board gate, PMP supplier, ADT parse (needs the perf-table-count/compat changes), register read of version/counts/masks. Records the missing full hash and marker.
3. **C2, firmware pin**: add the measured `FirmwareBuild` for the installed stub. Admission passes; still no start. Proves identity pinning.
4. **C3, start with InitData graph as T6030 shape but J516C IO table + version + hw record size/view + hw tail words + overlay words** (this is the biggest single step; split it into the sub-boots below only if it fails): 
   - C3a: version word 0x0c08e21e84820490, J516C IO table (17 slots, repacked VAs), aligned/cached HwData at 0xfffffc20406fb580 with 0xb480 size and view +0xb400, fast-die mask 0x802a002b802a002b, pstate cap state 1. Expect READY ("runtime=1 newA=1/1" equivalent) possibly with MTR/alarm fatal as before (our t38/t39). Proves the initdata path on #358's boot code.
   - C3b: + J516C_HW_TAIL words; C3c: + overlay words (376/7/2). One per boot if C3a halts, in the order our results followed (t37 -> t38 -> t39 -> t41).
5. **C4, device controls + idle**: `DEVCTL 0x13/9` accepted, readiness, rings drain, idle policy (#358 `idle_standby_us` etc.). Proves power/idle on four clusters.
6. **C5, render node registered, no job**: GET_PARAMS returns chip 0x6031, variant C, 4x10 clusters, masks 0x3ff x4, `num_dies 1`, `max_frequency` from the ADT. Check agx3b Mesa (`vulkaninfo --summary`, expect no `DRM_IOCTL_ASAHI_VM_CREATE` failure as in our t43).
7. **C6, first compute job**: G15C compute registers (all four: tail +0x2980, PTC 0x6000400020, DUPM 0x3c000000140, 0x1a0e9 = 0) and first-job-zero behaviour in `encode_compute`, with the Mesa USC-window fix; one change = register set. Proves compute (the `GREEN` check in results t83).
8. **C7, compute check suite**: the wordmap/witness checks of t83 at N=1024 and 8192. Proves 40 cores all get work.
9. **C8, render attempt**: only after C7. G15C TA/FS register values are UNKNOWN (see table); first boot uses the G15S values with `NO_VERTEX_CLUSTERING` (single cluster) to see if the firmware accepts a trivial pass; any halt is a trace task, not a guess. Then kmscube / a minimal render check.
10. **C9, stack**: display (`t6031/dcp-image`) + GPU together, `modprobe asahi` after the native display, then the render check against the agx3b Mesa, then kmscube on the built-in panel (map #18 destination).

Each of C1-C9 is one code change and one boot; failed ones are a stop-and-measure, never a parameter sweep (our own stop rule from t83).

## 5. Risks and open questions

1. **(INFERRED, high)** Replacing the hash-pinned T6030 board templates is the real porting cost; #358's engine assumes template offsets (e.g. DVFS tables at +0xb5c/+0xf9c/+0x1350, voltages +0xb9c/+0xd9c, top freq +0x4dc4, `CACHED` 0x4a04, `FAULT_INFO` 0x8900, HwDataA S8 words) that are for the 0x8a04 record. The J516C record is 0xb480 and its DVFS/voltage tables are at the offsets our fork found (`m3_adt_config.rs` log_tables, J516C words at +0x1060, +0x1160, +0x1394.. per t40 README). Whether DVFS/voltage offsets coincide between the two records is UNKNOWN until the J516C records are diffed.
2. **(OBSERVED then INFERRED)** MTR alarm: on T8122/J516C the firmware's alarm handler does a 64-bit atomic at HwDataA +0x4350; unaligned or uncached HwData faults (`m3_soc.rs:408-414`). #358 places HwData at an unaligned VA (0x...5fc) with only the first 0x4a04 cached. It works on T6030 because the T6030 alarm mask is zero. On J516C we boot with fast-die mask 0x802a002b802a002b, alarm 0; if #358's placement is kept the same fault could return. Mitigation: use our aligned/cached placement.
3. **(OBSERVED)** Firmware pin drift: results from 2026-10-12 show iBoot-10151.140.19.700.2 on this M3, and the brief says .702.3 now. The stub may have been replaced; the TEXT hash has to be re-measured on the stub in the EFI/boot chain actually used. Our recorded prefix 0xc26ec89c1150eb65 predates that and cannot be assumed current.
4. **(INFERRED)** ADT shape: `adt.rs` parse is strict (`gpu,t6030`, nub equality, 14 perf states, one table, fixed constants incl. `gpu-power-sample-period 8`). J516C may fail any of these; each failure is an admission refusal (safe, no firmware write) so C1 is cheap.
5. **(OBSERVED)** #358's PMP bring-up (display hold, AGX vote, DCS4/FAB2 memory floor, PTD requests) is T6030-hardware specific (PA 0x3503c0000, indices 280/284, etc.); our J516C uses the kit's PMP image and `apple_pmp_set_device_power(0x0f,5,1)`. The two must not both run. A display-hold/memory-floor equivalent may also be needed for the GPU on J516C (our t72 "display floor" boot touched this).
6. **(INFERRED)** The 40-core registers: DUPM 32N|96N<<32, tail 0x2980, PTC are compute-only evidence. Render needs the same class of data (4 clusters; partial-render, clustered TA, M1..M4 buffers sized for 2 clusters, `PB_*` pools, preemption records 3 vs more). Expect the render step to need a trace, not a guess.
7. **(OBSERVED)** `g15_stream_gate` defaults on: it admits only known CDM/VDM stream records from the T6030-qualified Mesa. G15C launch records differ (word0/word3, USC base-page); the gate will refuse them until extended. Mesa side: the G15C USC-window base page fix is not in the kernel.
8. **(OBSERVED)** Clean-room: #358 is a second tree in the same family. Provenance stays in our fact records; commit text cites public sources and measurements only (ADR 0001). Reading #358's code for structure/values is allowed; copying its expression is not.
9. **Open**: does the m1n1 we boot export the `adt` phram label on T6031? Does `max/t6031-*` m1n1 leave the firmware `pre-loaded`? Is the GFX power domain handled by `ps_gfx` the same (phandle synthesized in #358 because the bootloader DT lacks one)? Is the J516C 40-bit enabled-core mask read via +0xe01504 correct for binned SKUs (J516C is the 16-CPU 40-core)? Is 4 clusters x 10 the same on J514C (30-core)? (not tested)
10. **Team decision pending** (memory: aurora-cleanroom-kernel-tree): Eryk chose the C-language clean-room tree (`drm/apple/gpu-g15-*`) on 2026-10-13; this Rust `g15/` module in aurora-silicon/linux is a different, newer line. Which tree T6031 lands in needs confirming before investing in the port.
