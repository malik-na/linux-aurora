# Does this Mac's DCP firmware speak the same display interface as the M3 Pro's?

Research for [malik-na/linux-aurora#23](https://github.com/malik-na/linux-aurora/issues/23) (parent #18). Date: 2026-10-12.

Clean-room (ADR 0001): no Apple firmware, IPSW, installer or driver contents were extracted, decoded, disassembled or read. Sources are the Asahi and fork kernel source, m1n1 source, the fork's commit messages and the `agent-docs` boot logs. The only thing read on the M3 (`ssh m3`) was non-root `/proc/device-tree/chosen` text properties (the image UUIDs and OS-firmware label). No serials, MACs or credentials appear here.

Labels: **[E]** a cited source says so. **[I]** my inference, not proven.

Pinned sources:
- Fork: `malik-na/linux-aurora` `t6031/pmp-image` @ `fe2063efc3a4` (link labels like `iomfb_v14_7.c#L50` point into `drivers/gpu/drm/apple` at this commit).
- Asahi kernel: `AsahiLinux/linux` `asahi` @ `77cb8f24c238` (labels prefixed `U/` point into its `drivers/gpu/drm/apple`).
- m1n1: `AsahiLinux/m1n1` @ `57a9339ffd18`. Asahi docs: `AsahiLinux/docs` @ `0d1f8917fa88`.

## Short answer

1. **Upstream selects the IOMFB interface by firmware-compat version, never by SoC [E].** One `fw_compat` enum picks one method table plus one callback table (12.3 or 13.5). The SoC only changes a DPTX port count. The same 13.5 tables serve M1, M1 Pro/Max and M2 DCPs. Upstream has no 14.x template and no image pinning at all, so it cannot tell us how T6030, T8122 and T6031 relate.
2. **"14.7.0" is a coarse label, not an image identity [E].** m1n1 derives `firmware-compat` from the OS firmware version of the booted stub, the same for every DCP in the tree. All three M3 families here (T6030, T8122, T6031) carry the 14.8.3 stub and the 14.7 label, yet have three different DCP image UUIDs. A shared label says "same OS release", not "same bytes", so the label cannot be the guard. The fork pins the UUID instead.
3. **The fork's own evidence that T6030 and T8122 images share a layout is real but one-sided [E/I].** The identical `iomfb_v14_7.c` code (start, swap, callbacks, property handling) has run on T6030 and on T8122 (J613). The only per-image difference the fork ever wrote down is the colour-matrix method pair (J613 A421/A420), and nothing says T6030's differ; it was left unset "for now". Nothing in the repo shows a layout difference between the images. Nothing shows the J516C image was ever checked either.
4. **Admitting `F493F03E` for J516C needs only the UUID in the board record, plus test and comment updates [E].** There are no per-image offset tables to fill in: every method number and struct offset is a file-level constant; the board record's only per-image fields are `ctm_set`/`ctm_get`, which J516C leaves at 0.
5. **Recommendation: yes, one test boot admitting `F493F03E` is a sound next step, as one change per boot [I].** The driver fails closed on a mismatch and leaves the boot framebuffer, and the first dozen log lines say clearly whether the interface matched. Read the caveats in section 5: the kernel's modeset is a no-op, so the first real layout test is the first swap, which happens right after "display started".

## 1. Asahi: interface per firmware version, not per SoC

### The version is parsed from the device tree, and SoC does not enter [E]
- `dcp_check_firmware_version()` reads `apple,firmware-compat` (and the informative `apple,firmware-version`) and returns 12.3 or 13.5 from the string alone. It never looks at a SoC compatible. [`U/dcp.c#L938-L971`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/dcp.c#L938-L971). The only wrinkle is a version-string one: compat "13.3" with firmware "13.5.0" counts as 13.5 (L956-L966).
- The result is stored as `dcp->fw_compat` ([`dcp.c#L1163-L1179`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/dcp.c#L1163-L1179)), an enum with exactly `V_12_3` and `V_13_5` ([`dcp-internal.h#L30-L34`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/dcp-internal.h#L30-L34)).
- Every IOMFB entry point switches on that enum only, for example modeset ([`iomfb.c#L432-L442`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb.c#L432-L442)) and the start/swap/power entry points ([`iomfb.c#L481-L505`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb.c#L481-L505), [`#L547-L556`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb.c#L547-L556)).
- The two interfaces are two compile-time templates, `iomfb_v12_3.c` and `iomfb_v13_3.c`, each defining `DCP_FW` and its own method table and callback table. Their method numbers differ: set-create-dfb is `A357` in 12.3 and `A373` in 13.3 ([`iomfb_v12_3.c#L13`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb_v12_3.c#L13), [`iomfb_v13_3.c#L13`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb_v13_3.c#L13)). Callback numbers move too: get_time is `[208]` in 12.3 and `[209]` in 13.3 ([`iomfb_v12_3.c`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb_v12_3.c), [`iomfb_v13_3.c`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb_v13_3.c)).

### SoC only changes a port count [E]
- `struct apple_dcp_hw_data` has one field, `num_dptx_ports` ([`dcp-internal.h#L112-L114`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/dcp-internal.h#L112-L114)). The `of_match` table maps `apple,t6020-dcp`, `apple,t8112-dcp`, `apple,dcp` and `apple,dcpext` to values of it ([`dcp.c#L1342-L1362`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/dcp.c#L1342-L1362)).
- DT nodes: M1 `apple,t8103-dcp` ([`t8103.dtsi#L646-L647`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/boot/dts/apple/t8103.dtsi#L646-L647)), M2 `apple,t8112-dcp` ([`t8112.dtsi#L737-L738`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/boot/dts/apple/t8112.dtsi#L737-L738)), M1 Pro/Max `apple,t6000-dcp` ([`t600x-common.dtsi#L515-L516`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/arch/arm64/boot/dts/apple/t600x-common.dtsi#L515-L516)). Each lists the generic `apple,dcp` fallback, so the same code and the same `fw_compat` tables apply to M1, M1 Pro/Max and M2 DCPs.
- So an M1 DCP, an M1 Pro DCP and an M2 DCP all running firmware-compat 13.5 are driven by the one `iomfb_v13_3` template. **[E]** for the code path. **[I]** that this works equally well on all of them in the field: the repo tells us it is selected, not that every SoC was tested (Asahi ships it on all three).
- One in-template note that a SoC-specific quirk exists within a version, but not a layout one: "t8103-dcp crashes without setting this immediately during modeset on 12.3 and 13.5 firmware" ([`iomfb_template.c#L687-L691`](https://github.com/AsahiLinux/linux/blob/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple/iomfb_template.c#L687-L691)), a value written the same way for every SoC.

### `firmware-compat` comes from the OS firmware version, not from the DCP image [E]
- m1n1 writes both properties into every DCP node. `apple,firmware-version` is the detected OS firmware; `apple,firmware-compat` is a lookup from it (12.3.1 and 12.4 to 12.3; 13.5 beta4, 13.5, 13.6.1 to 13.5; 14.7 to 14.7). The table holds no chip. [`m1n1 src/kboot.c#L1541-L1578`](https://github.com/AsahiLinux/m1n1/blob/57a9339ffd1876e78297b17d34dece8cff8fa1ba/src/kboot.c#L1541-L1578).
- Asahi's docs say the same from the user side: Asahi Linux "behaves as if it were macOS 12.3/12.4/13.5 (depending on model and installation time)" ([`sonoma-display-bug.md`](https://github.com/AsahiLinux/docs/blob/0d1f8917fa88745d62a4c05d802c4a7298c8616b/docs/sw/sonoma-display-bug.md)). The model enters only through the OS version it was installed with.
- Asahi also states the ABI has no stability promise across releases: "the firmware ABI for these coprocessors has no stability guarantees whatsoever" ([`platform/introduction.md` L104](https://github.com/AsahiLinux/docs/blob/0d1f8917fa88745d62a4c05d802c4a7298c8616b/docs/platform/introduction.md?plain=1#L104)). That is why the version is the key, and why a label that covers several releases (next section) is weak.

### What upstream does not tell us [E]
- No `iomfb_v14*` file exists in `AsahiLinux/linux` `asahi` ([directory listing](https://github.com/AsahiLinux/linux/tree/77cb8f24c2381a8abb7272d7bbdec548d6426a8a/drivers/gpu/drm/apple)); there is no M3 DCP support, and no UUID pinning anywhere in the driver. Upstream admits any image whose compat string matches. So "which images upstream admits for which boards" has the answer: all of them, for the versions it knows (12.3, 13.5); none for 14.x.

## 2. The fork: what is pinned, where, and why

### The two UUIDs and who admits what [E]
- `DCP_V14_FIRMWARE_UUID` = `DDF38191-93B3-324A-BC8F-643006F5AC82`, commented `/* T6030 */`; `DCP_V14_J613_FIRMWARE_UUID` = `90F849E1-B422-367E-B389-50246F8DEC47`, commented `/* J613 */`. [`iomfb_v14_7.c#L50-L52`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L50-L52). The comment above them reads: "The images whose method and callback layouts this file implements."
- Boards ([`iomfb_v14_7.c#L68-L136`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L68-L136)):

| Board record | DCP compatible | Machine | Image admitted |
| --- | --- | --- | --- |
| T6030 (J514S, J516S) | `apple,t6030-dcp` | any | `DDF38191` |
| J613 | `apple,t8122-dcp` | `apple,j613` | `90F849E1` |
| J615 | `apple,t8122-dcp` | `apple,j615` | `90F849E1` (same image, per the comment "the same DCP image") |
| J516C | `apple,t6031-dcp` | `apple,j516c` | `DDF38191` (the T6030 image) |

- Admission is a single `strcmp` against the one `firmware_uuid` string in the record ([`iomfb_v14_7.c#L1430-L1433`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L1430-L1433)), run first in the probe, before the handoff marker, DART, CPU, PMP checks ([`#L1466-L1486`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L1466-L1486)). The record type has one `firmware_uuid` field described as "The firmware image whose layouts were tested on this board" ([`iomfb_v14_7_board.h#L22-L23`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7_board.h#L22-L23)).
- The compat check in `dcp.c` is a separate and wider gate: any internal 14.x board record accepts exactly `14.7.0` ([`dcp.c#L1916-L1927`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/dcp.c#L1916-L1927)). That one already passes on this Mac: the refusal comes from the UUID check, not the compat check ([`t17 boot log`](https://github.com/malik-na/linux-aurora/blob/agent-docs/work/t6031-kit-refusals/results/20261012-220921-t17-display-pmp/collect.txt#L39): `J516C display not started: DCP firmware F493F03E-CC40-3D89-9A08-5F259BA2B246 is not supported`).
- This Mac's own images: `dcp` and `dcpext0..3` are all `F493F03E-CC40-3D89-9A08-5F259BA2B246`; `gfx` and `pmp` are other UUIDs. Seen in the boot log ([`collect.txt#L12-L26`](https://github.com/malik-na/linux-aurora/blob/agent-docs/work/t6031-kit-refusals/results/20261012-200132-t03-back-to-normal/collect.txt#L12-L26)) and confirmed today in `/proc/device-tree/chosen/asahi,t6031-fw-uuids` (the same UUIDs), with `asahi,os-fw-version` = `14.7`.
- `dcpext` (the external-display processors) has its own, narrower pin: T6030 external processors need `DDF38191` ([`iomfb_v14_7.c#L1763-L1766`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L1763-L1766), [`dcpext_scanout.c#L770`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/dcpext_scanout.c#L770)). T6031 has no `dcpext` match entry ([`dcp.c#L2804-L2816`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/dcp.c#L2804-L2816)), so this does not touch J516C.

### Why pinned by UUID: the stated reasons [E]
- Original T6030 pin: one UUID, "The image whose method and callback layouts this file implements", added with the T6030 bring-up ([`107036c9c167`](https://github.com/malik-na/linux-aurora/commit/107036c9c167): "Bring up the T6030 internal panel and notch, the DCP 14.7 IOMFB interface and the external display"). It was validated on J514S/J516S hardware (the later swap commit still says "pending the J516S hardware check", [`29095d9d22dd`](https://github.com/malik-na/linux-aurora/commit/29095d9d22dd)).
- J613 pin (`57204a7ce451`): the record holds "the firmware image tested on the board"; it "replaces the earlier T8122 admission, which accepted either firmware image together with either boot loader marker on any T8122 machine". So a looser rule existed and was deliberately tightened to one image per board. Validation: "The J613 record has run on a J613 with 14.x system firmware." [commit](https://github.com/malik-na/linux-aurora/commit/57204a7ce451). J615 reuses the J613 image ([`7d5a612eceaa`](https://github.com/malik-na/linux-aurora/commit/7d5a612eceaa): "Select the existing T8122 14.x DCP image on the 15-inch M3 Air, retaining the firmware UUID").
- CTM pin (`10cb090a1a75`): "The colour matrix methods are per firmware image, so the board record names them: on the J613 14.x image the setter is A421 and the getter A420. Records without them (T6030 for now ...) send nothing." and "so that only tested firmware images get them". Tested: "Tested on J613 (14.x firmware): night light warms the panel." [commit](https://github.com/malik-na/linux-aurora/commit/10cb090a1a75). The header repeats it: "Method numbers differ between firmware releases, so they are only set where tested." ([`iomfb_v14_7_board.h#L36-L41`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7_board.h#L36-L41)). Note the word is *releases*, and no T6030 value is ever given.
- J516C pin (`8b964861dace`): "Only the T6030 DCP image (DDF38191-...) has validated IOMFB layouts, so the record admits that image only. A J516C DCP with any other image is refused at probe, before the PMP is started or the DCP touched, with one line naming the image it has; the boot framebuffer stays." [commit](https://github.com/malik-na/linux-aurora/commit/8b964861dace); same comment in the record ([`iomfb_v14_7.c#L113-L118`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L113-L118)). That commit deliberately made the refusal a conservative default for a board with no prior hardware run; it is not a finding that F493F03E differs.

### Is there evidence the pin guards a real layout difference? [E] / [I]
- **Evidence for sameness (T6030 image vs T8122 image).** The two images belong to different SoCs and carry different UUIDs, yet one code path serves both. Every method and callback number is shared, and the board record does not carry them: the grep of `iomfb_v14_7.c` shows the code reads only `ctm_set/ctm_get`, panel size, `promotion`, `handoff`, `log_bringup`, `name` and `debugfs` from the record ([`iomfb_v14_7.c#L2412-L2439`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L2412-L2439) for the CTM use; the rest from the field list in [`iomfb_v14_7_board.h#L15-L42`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7_board.h#L15-L42)). The J613 image was run through that code on hardware: it starts, receives its mode catalog and swaps, and the CTM commit tested night light on top of it. The fork also has to handle one callback the J613 sent that the code had not needed to answer before: D208 ([`08bba63dfb41`](https://github.com/malik-na/linux-aurora/commit/08bba63dfb41): "The J613 firmware sends D208 after a colour matrix changes ... Other callback layouts remain unchanged"). The handler is unconditional ([`iomfb_v14_7.c#L880-L889`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L880-L889)), not board-gated.
- **Evidence for difference: none found.** The nearest candidate is the CTM pair: J613 uses A421/A420 and T6030 is left unset. That is "not yet tested", not "different". Nothing in the commit messages or comments records a method number, callback size or struct offset that differs between the T6030 and T8122 images.
- **Evidence the pin is plain caution [I].** The language is "tested", "validated", "fails closed" ([`iomfb_v14_7_board.h#L10-L12`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7_board.h#L10-L12): "another board's record enables only what was tested on it, and anything else fails closed"), never "differs". Per-UUID pinning guards the *possibility* of a drift between images, which Asahi's own docs warn about (section 1), and which the 12.3 vs 13.3 tables show is real across *versions*.
- The label argument: T6030 (J516S, [omacom#47 comment](https://github.com/omacom/linux-aurora/issues/47#issuecomment-6114255901): `os-fw-version 14.7`, stub 14.8.3 build 23J220), T8122 (J613/J615, "14.8.3 stub", [M3-GPU.md L1-L4](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/tools/aurora-sep/M3-GPU.md?plain=1#L1-L4)) and T6031 (this Mac: stub 14.8.3 per [#13](https://github.com/malik-na/linux-aurora/blob/research/macos-same-gpu-firmware/findings.md), `os-fw-version 14.7`, `firmware-compat 14.7.0`) all share the OS release and the label. They still ship three DCP UUIDs, so the UUID is per SoC (and per image build). **[I]** Same OS release makes a shared interface likely but does not prove it: the same-release T6030 and T8122 pair is the only data point, and it points to "shared".

## 3. What admitting `F493F03E` for J516C needs

### Code [E]
1. `iomfb_v14_7.c`: add a UUID define and set `.firmware_uuid` of `dcp_v14_board_j516c` to `F493F03E-CC40-3D89-9A08-5F259BA2B246` ([`#L119-L130`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L119-L130), the field at L124). Rewrite the comment at [`#L110-L118`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L110-L118): it currently says only the T6030 image has validated layouts; it must say the layouts are unvalidated on this image and name the source of the assumption (ADR 0001: "every firmware interface value ... names its source in a code comment"): same firmware-compat 14.7.0, same OS release, Asahi's per-version design, and the T6030/T8122 shared-code evidence above.
2. Nothing else is image-specific. Methods and callbacks are file-level constants (`A(n)`/`D(n)`, exact-size `SHAPE(in,out)` checks, [`iomfb_v14_7.c#L879`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L879)), and the swap record offsets are fixed header constants (`DCP_V14_SWAP_SIZE 0x1b58`, `DCP_V14_SWAP_ID 0x98`, ... [`iomfb_v14_7_swap.h#L9-L26`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7_swap.h#L10-L24)). Per-image offsets exist only for the CTM pair (record fields `ctm_set`, `ctm_get`), which stay 0 for J516C as today ([`v14-board-test.c#L70-L72`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/v14-board-test.c#L70-L72)). **If** the test boot shows a mismatch, the fix would be to move the mismatching constant into the record, as was done for CTM, with the evidence for each.
3. `dcp.c` needs no change (compat 14.7.0 already passes, [`L1916-L1927`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/dcp.c#L1916-L1927)); neither do `dcpext_scanout.c` or the external-processor pin.

### Tests that encode the old pin and must change in the same commit [E]

- A failed call sets `failed`, stops the link, and keeps the boot framebuffer; the session is one-shot, so recovery is a reboot ([`L289-L296`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L289-L296), [`L2386-L2390`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L2386-L2390), [`L2109-L2116`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L2109-L2116)).

## 5. Recommendation and caveats

**Recommended next step: one test boot, changing only `.firmware_uuid` to `F493F03E` (plus the matching tests and comment), with Naeem's go-ahead per the map's M3 safety rule.** Reasons:
- The strongest design evidence we can get without a trace agrees with the change: interfaces are keyed by firmware version (section 1), this Mac's compat is the same 14.7.0, and two other SoC images with the same label share all code paths here (section 2).
- Nothing on record suggests a difference, and the admission guard was written as "tested", not "differs" (section 2).
- Failure modes are loud, early and recoverable (section 4); the PMP and DCP session are touched only after the UUID gate, so this boot is the first time this driver starts the PMP and wakes the DCP RTKit session on this Mac (the PMP layout checks already passed, #17), and the boot framebuffer stays on any start failure before "display started".

Do not widen the change: leave `ctm_set`/`ctm_get` at 0, panel numbers as they are, and the clock as the logged T6030 value. The clock and the panel (3456x2234, 74 notch rows, `promotion`) are separate unknowns; they would otherwise blur a failure with an image question.

Caveats [I]:
- **The first real layout test is the first swap, not "display started".** The DCP DRM driver replaces simpledrm once it starts, so fbcon or the compositor will submit a swap (`A406`/`A407`, a `0x1b58`-byte record with fixed offsets) right after the `display started` line. The link checks sizes and the swap id echoed by the D589 completion ([link.c L387-L388](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7_link.c#L387-L388), [L486-L497](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7_link.c#L486-L497)), but a same-size record with shifted fields would be accepted by the transport and fail only on screen (black or stale frame) with `display refused a swap` ([L2569](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L2569)) or `native DCP flip failed` ([L2574](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L2574)) or silence. Worth reading `/sys/kernel/debug/dcp-j516c` (`swaps`, `failed`, `swap_max_us`; [`L2237-L2260`](https://github.com/malik-na/linux-aurora/blob/fe2063efc3a409d98e149b8466cedb8efd40e03f/drivers/gpu/drm/apple/iomfb_v14_7.c#L2235-L2266)) over the proxy/ssh in the same boot. I did not find a knob to hold off the first swap.
- The "same label means same interface" argument rests on two other SoC images; there is no third image to cross-check, and no primary source says the T6030 and T8122 images are identical in layout. It is the best-supported hypothesis, not a proof.
- A clean success is evidence for `F493F03E`'s layout, and the correct evidence to record in the code comment afterwards. A failure names the first diverging method or callback (tag and sizes are printed), which is exactly the input for a per-image constant.
- Clean-room: a mismatch would be resolved from the logged tag and sizes, ADR 0001's source order (device-control test, maintainers, crash log's known sections, then a hypervisor trace), not by reading Apple code.
